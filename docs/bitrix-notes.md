# Заметки по Битрикс: что и почему исключено/включено

Каждое новое расширение/каталог в профиле сопровождается строкой здесь
с обоснованием (правило AGENTS.md, раздел 12). Ниже — решения, принятые
при реализации профиля `bitrix` (фазы 1–3).

## Категории и классификация

- **Расширение `.key` отнесено к категории `keys`** (а не к `slides`/Keynote,
  как допускала спека в двух списках). На Linux-стенде файл `.key` почти
  наверняка приватный ключ; ложное срабатывание безопаснее пропуска.
  Из `slides` расширение убрано.
- **Двойные расширения** (`.tar.gz`, `.tar.bz2`, `.tar.xz`, `.sql.gz`) проверяются
  до одинарных — `.tar.gz` классифицируется как `archives`, а не `.gz`.
- **Каталог как критерий категории** (расширение модели `Category.dirs`):
  «всё содержимое `bitrix/backup/`» и «логи/кэш» (`bitrix/tmp`, `upload/tmp`,
  `bitrix/cache`, `bitrix/managed_cache`, `bitrix/stack_cache`, `bitrix/html_pages`)
  невозможно выразить расширениями — добавлены поля `dirs` (каталог категории),
  `paths` (точные относительные пути), `name_patterns` (fnmatch на имя:
  `.env.*`, `*.log.*`, `.~lock*`). Приоритет: пути → имена → шаблоны → каталоги →
  расширения (двойные раньше одинарных).
- **`only_under` по-разному**: в спеке он на уровне категории, но для `docs`
  ограничены только `.txt`/`.md`, а для `sheets` — только `.xml`/`.json`/`.yaml`/`.yml`.
  Добавлено поле `ext_only_under` (расширение → разрешённые каталоги);
  `only_under` (вся категория) сохранено для совместимости со спекой.
- **`.txt`/`.md` вне `upload/` игнорируются** — корневые readme/docs проектов
  не ПДн и трогать их нельзя.
- **`.csv`/`.tsv`/`.xls`* везде** (не только под `upload/`) — выгрузки могут
  лежать в любом месте; риск высокий.
- **Изображения (`.jpg .png .gif .webp .svg …`) намеренно не включены** —
  на публичном сайте это контент, а не ПДн; включение сломало бы принцип
  «не ломать CMS».
- **`media` выключена по умолчанию** (`default_enabled=false`) — аудио/видео
  чаще контент, чем утечка; включается вручную.

## Исключённые каталоги

Точно по спеке (раздел 6.2): `bitrix/modules|components|templates|js|themes|
wizards|gadgets|activities|panel|images|css|fonts`, `vendor/`, `node_modules/`,
`.git/`, `.svn/`, `.hg/`, `.idea/`, `.vscode/`, `upload/resize_cache/`.

- Сопоставление — по **непрерывным частям пути**: работает и Битрикс в
  подкаталоге (`www/site/bitrix/modules`), и вложенные `vendor/` (например,
  `local/vendor/`). `local/` НЕ исключён целиком — там пользовательские
  выгрузки/логи, которые нужно находить.

## Рискованные каталоги (только пометка в отчёте/GUI)

`upload/{webform,form,sale,crm,support,mail,tasks,disk,1c_exchange,1c_catalog,
iblock,main,medialibrary}`, `bitrix/backup` — раздел 6.3, без изменений.

## Скрытые файлы

- `.env`, `.env.*`, `.htpasswd`, `.my.cnf`, `.pgpass`, `.netrc`,
  `bitrix/.settings.php`, `bitrix/.settings_extra.php` — **скрытые/точечные
  файлы**: по умолчанию сканер их пропускает. Для отчёта о секретах нужен
  `--include-hidden` (в GUI — чекбокс «Скрытые файлы»). Это осознанно:
  работа со скрытыми файлами — отдельное явное решение оператора.
- `bitrix/php_interface/dbconn.php` — не скрытый, находится всегда и попадает
  в `secrets_report` (только отчёт, действия запрещены на уровне ядра).

## Поведение действий

- ZERO сохраняет uid/gid/mode/atime/mtime — запись `b_file` остаётся валидной,
  сайт не ломается; пустые файлы пропускаются (`skipped_empty`).
- Симлинки никогда не обрабатываются (`skipped_symlink`), цель не трогается.
- Повторный запуск идемпотентен: ZERO → `skipped_empty`, DELETE → `already_absent`.
- STUB: `.pdf` → минимальный валидный PDF с текстом `SANITIZED`;
  `.zip/.docx/.xlsx/.pptx` → пустой zip-контейнер; `.txt/.csv/.tsv/.md/.log` →
  перевод строки; остальные — как ZERO.
- `report_only`-категории фильтруются до действий в CLI **и** повторно
  защищены внутри `actions.py` (двойной рубеж).

## Скрытые риски и ограничения (на текущую фазу)

- Файлы в `.git/` не сканируются, но остаются в истории Git — при наличии
  репозитория в корне требуется отдельная чистка истории (план: фаза 6).
- Карантин/восстановление, TUI, упаковка AppImage — фаза 6 по плану AGENTS.md.

## Фаза 6: карантин, restore, SQL b_file, TUI

- **Карантин** (`--quarantine DIR`): tar.gz в DIR (проверяется вне корня и в
  CLI/GUI через `safety.check_quarantine_dir`, и в ядре — по включению путей
  файлов). Внутри архива `manifest.json`: исходный путь, размер, sha256,
  uid/gid/mode/mtime, категория. Оригиналы удаляются после упаковки.
  Отмена до старта не создаёт пустой архив.
- **`sanitize restore ARCHIVE [--dry-run]`**: восстановление по манифесту;
  member-имена плоские (`files/NNNNNN.ext`) с проверкой на path traversal;
  существующие файлы НЕ перезаписываются (`exists`); права/mtime
  восстанавливаются, владелец — best-effort (без root пропускается).
- **SQL для `b_file`** (`--sql FILE`): только для реально обнулённых файлов
  под `upload/`; `UPDATE b_file SET FILE_SIZE = 0 WHERE FILE_NAME = '...'
  AND SUBDIR = '...' AND FILE_SIZE > 0` (идемпотентно). Файлы вне `upload/`
  помечаются комментариями. Скрипт выполняется вручную на БД — утилита
  к БД не подключается.
- **Предупреждение о `.git`**: если в корне есть `.git`, CLI печатает
  предупреждение всегда, GUI добавляет его в диалог подтверждения:
  обнуление/удаление не убирает файлы из истории репозитория.
- **TUI** (`--tui`, extras `tui`): путь, чекбоксы категорий, таблица
  найденного, обнуление/удаление с подтверждением (для удаления — ввод
  `DELETE`). Действие применяется ко всем найденным файлам выбранных
  категорий — для точечной работы используйте GUI/CLI.
- AppImage в 1.0.0 не собирается (AGENTS.md, раздел 2: «отдельная задача»);
  дистрибуция — pipx/uv.

## Фаза 5: сигнатуры, deep-scan, .sanitizeignore, многопоточность

- **magic (`--magic`)**: применяется только к файлам, не распознанным по
  имени/расширению (включая файлы без расширения); MIME -> категория
  (`application/pdf` -> docs и т.д.). Без python-magic/libmagic — предупреждение
  один раз, не падение. Отключённые категории (например, media) через magic
  не включаются.
- **deep-scan (`--deep-scan`)**: текстовые форматы (.csv .tsv .txt .md .xml
  .json .yaml .yml .log .sql .eml .vcf) и office-контейнеры (.docx —
  `word/document.xml` + `word/sharedStrings.xml`; .xlsx — `xl/sharedStrings.xml`).
  Паттерны: e-mail, телефон РФ, паспорт РФ (с разделителями), СНИЛС/ИНН
  (с контрольными суммами), карта (Луна). Лимит чтения 20 МБ/файл
  (`ScanOptions.content_read_limit`). Счётчики — `content_hits` в отчёте
  (JSON/MD/GUI). Кодировка — UTF-8 (errors=ignore); cp1251-дампы могут
  давать заниженные счётчики.
- **`.sanitizeignore`** в корне проекта: подмножество gitignore (комментарии,
  `dir/`, якорные `/путь`, `**`, `*`, `?`). Отрицания `!` не поддерживаются.
  Применяется всегда, до классификации; каталог по шаблону исключает поддерево.
- **Многопоточный обход** (`threads > 1`): ThreadPoolExecutor по подкаталогам
  первого уровня корня. Замер на дереве 205k файлов: single ~4.5 с, threads=4
  ~4.7 с — ускорения нет (обход CPU-bound в Python, GIL), результаты
  идентичны; параллелизм даёт эффект на медленных ФС (NFS/CIFS) и остаётся
  заделом под будущий ProcessPool.
- Производительность однопоточного скана: ~45-50k файлов/с на локальной
  ext4/overlayfs (дерево 205k файлов ~4.5 с).
